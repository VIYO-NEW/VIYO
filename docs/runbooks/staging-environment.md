# Staging Environment Runbook

**Authority:** VIYO Final Doc1 Master PRD lines 9690-9700, VIYO Final Doc11 Security Architecture line 43, and T90 / SEC-10 Builder Execution Brief dated 2026-04-30.

**Scope:** This runbook describes the Phase 3 staging environment for VIYO. It does not change the production deployment path, production domains, or production credentials. The production deploy workflow remains `.github/workflows/deploy.yml`; staging uses `.github/workflows/deploy-staging.yml` and the `develop` branch.

## Locked Staging Topology

The staging environment is a separate deployment lane that receives code from `develop`. Production remains governed by the existing `main` branch and manual PO promotion path. Staging must use a separate Supabase project, staging-only environment variables, staging-only Inngest keys, and synthetic test data only.

| Surface | Production | Staging | Branch / Trigger | Ownering System |
|---|---:|---:|---|---|
| Public website | `https://viyo.new`, `https://www.viyo.new` | `https://staging.viyo.new` | `develop` auto-deploys staging | Vercel project `viyo-web`, Preview branch domain |
| Brands app | `https://app.viyo.new` | `https://app.staging.viyo.new` | `develop` auto-deploys staging | Vercel project `viyo-web`, Preview branch domain |
| Admin app | `https://admin.viyo.new` | `https://admin.staging.viyo.new` | `develop` auto-deploys staging | Vercel project `viyo-admin`, Preview branch domain |
| Worker API | `https://api.viyo.new` | `https://api.staging.viyo.new` | `develop` auto-deploys staging | Render service `viyo-worker-staging` |
| Database/Auth | Production Supabase project | Separate staging Supabase project | Migrations applied independently | Supabase dashboard / CLI |
| Data policy | Production data | Synthetic data generated by `@faker-js/faker` | `pnpm --filter @viyo/db seed:staging` | `packages/db/scripts/seed-staging.mjs` |

## Supabase Staging Project

Create a completely separate Supabase project for staging. The project may use the free tier if it satisfies current load and retention needs. Never reuse production connection strings, production JWT secrets, production service-role keys, or production auth redirect URLs.

| Setting | Required Staging Value |
|---|---|
| Project name | `viyo-staging` or an unambiguous equivalent |
| Project URL | `https://[staging-project-ref].supabase.co` |
| Auth redirect URL | `https://app.staging.viyo.new` |
| Additional auth redirect URL | `https://staging.viyo.new` for public staging flows and `https://admin.staging.viyo.new` if admin auth is enabled |
| Database migration source | Existing repo migrations in `packages/db/drizzle/` |
| Data source | Synthetic-only seed generated by `@faker-js/faker` |

Apply schema migrations to staging with the same migration set used by production. The expected command from the repo root is shown below after exporting the staging database URL. This command must run against the staging project only.

```bash
export DATABASE_URL='postgresql://STAGING_DATABASE_URL_FROM_SUPABASE_POOLER'
pnpm --filter @viyo/db db:migrate
```

After migrations succeed, seed synthetic staging fixtures. The seed command has explicit safety guards and refuses to run unless `VIYO_SEED_TARGET=staging` and `VIYO_ALLOW_STAGING_SEED=true` are present. It also rejects production-like connection strings.

```bash
export DATABASE_URL='postgresql://STAGING_DATABASE_URL_FROM_SUPABASE_POOLER'
export VIYO_SEED_TARGET=staging
export VIYO_ALLOW_STAGING_SEED=true
pnpm --filter @viyo/db seed:staging
```

## Render Staging Worker

The staging worker is declared in `render.yaml` as `viyo-worker-staging`. It uses the same Dockerfile and Docker context as production, but it tracks `develop`, uses the staging custom domain, and receives only staging environment values in the Render dashboard.

| Render Setting | Staging Value |
|---|---|
| Service name | `viyo-worker-staging` |
| Branch | `develop` |
| Runtime | Docker |
| Dockerfile path | `apps/worker/Dockerfile` |
| Docker context | `.` |
| Health check path | `/health` |
| Custom domain | `api.staging.viyo.new` |
| GitHub Actions deploy hook secret | `RENDER_STAGING_DEPLOY_HOOK_URL` |

Render environment variables must be populated from `.env.staging.example`, using staging values only. Database, Supabase, Inngest, Redis, R2, Stripe, Sentry, and vault credentials must all be staging-specific. If a staging equivalent does not yet exist, leave the staging deployment blocked rather than copying a production value.

## Vercel Staging Configuration

Configure the Vercel **Staging** environment for both `viyo-web` and `viyo-admin`. The production domain assignments must remain unchanged.

| Vercel Project | Root Directory | Staging Domains | Required Public Variables |
|---|---|---|---|
| `viyo-web` | `apps/web` | `staging.viyo.new`, `app.staging.viyo.new` | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_APP_URL`, `VITE_API_URL`, `VITE_SENTRY_DSN_WEB` |
| `viyo-admin` | `apps/admin` | `admin.staging.viyo.new` | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_APP_URL`, `VITE_API_URL`, `VITE_SENTRY_DSN_ADMIN` |

Set the staging branch rule to deploy `develop` to the Vercel Preview/Staging environment. `staging.viyo.new`, `app.staging.viyo.new`, and `admin.staging.viyo.new` must be configured as `develop` branch domains rather than Production domains. After all domains are added, wait for Vercel to complete domain assignment and SSL provisioning before treating browser verification as complete.

## Cloudflare DNS

Create CNAME records only after the Render and Vercel target hostnames are known. Vercel-facing records must be DNS-only. Do not create any retired hyphenated staging API alias.

| Hostname | Type | Target | Proxy Mode |
|---|---|---|---|
| `staging.viyo.new` | CNAME | `cname.vercel-dns.com` | DNS-only |
| `app.staging.viyo.new` | CNAME | `cname.vercel-dns.com` | DNS-only |
| `admin.staging.viyo.new` | CNAME | `cname.vercel-dns.com` | DNS-only |
| `api.staging.viyo.new` | CNAME | Render-provided target for `viyo-worker-staging` | DNS-only unless Render confirms proxied support |

Validate DNS after records propagate.

```bash
dig +short staging.viyo.new
dig +short app.staging.viyo.new
dig +short admin.staging.viyo.new
dig +short api.staging.viyo.new
```

## GitHub Actions Staging Deployment

The staging lane uses `.github/workflows/deploy-staging.yml`. It runs on pushes to `develop`, invokes the shared CI gate, triggers the Render staging deploy hook, polls `https://api.staging.viyo.new/health`, and records staging URL statuses in the workflow summary.

The following repository secrets must exist before the staging deploy workflow can complete.

| Secret | Location | Notes |
|---|---|---|
| `RENDER_STAGING_DEPLOY_HOOK_URL` | GitHub repository Actions secrets | Deploy hook for `viyo-worker-staging`, not production |
| App and admin Vercel secrets | Vercel dashboards | Configure under the Staging environment only |
| Staging Supabase and database secrets | Render and Vercel dashboards | Must point to the separate staging Supabase project |

## Validation Checklist

Staging is complete only when all validation evidence is collected. If any dashboard-only item is inaccessible, record it as an external blocker instead of weakening the production boundary.

| Gate | Command or Evidence | Passing Result |
|---|---|---|
| Branch | `git branch -a` | `develop` exists |
| CI trigger | Push to `develop` | CI runs on `develop` |
| Secret scan | Push to `develop` or local `python3 scripts/redacted_secret_scan.py` | No findings |
| Render blueprint | `grep -c '^  - type: web' render.yaml` | `2` services |
| Staging workflow | GitHub Actions UI | `deploy-staging.yml` runs on `develop` |
| Worker health | `curl -i https://api.staging.viyo.new/health` | HTTP 200 |
| Public website browser | Browser screenshot of `https://staging.viyo.new` | Page loads with valid SSL |
| Brands app browser | Browser screenshot of `https://app.staging.viyo.new` | Page loads with valid SSL |
| Admin browser | Browser screenshot of `https://admin.staging.viyo.new` | Page loads with valid SSL |
| Data policy | Supabase dashboard plus seed output | Synthetic fixture rows only; no production PII |
| DNS | `dig +short` for all staging hostnames | Expected Vercel/Render targets resolve |

## Rollback Procedure

Rollback must preserve the production boundary. Do not modify production DNS, production Render service settings, production Supabase, or production Vercel domains while rolling back staging.

| Failure | Rollback Action | Production Impact |
|---|---|---|
| Bad staging worker deploy | Revert the offending `develop` commit or redeploy the previous healthy Render staging deploy | None |
| Bad staging Vercel deploy | Promote the previous staging deployment in Vercel or revert `develop` | None |
| Bad staging database migration | Restore or recreate the staging Supabase project from migration history; do not touch production | None |
| Bad staging DNS | Remove or correct only staging CNAME records | None |
| Secret exposure in repo | Stop, rotate affected staging secret, remove exposure, rerun secret scan before push | None if production secrets were never used |

## Teardown Procedure

Use this procedure when staging must be decommissioned. Teardown is staging-only and must not delete or alter production infrastructure.

| Order | Teardown Step | Validation |
|---:|---|---|
| 1 | Disable auto-deploy for `viyo-worker-staging` in Render | Render dashboard shows staging auto-deploy disabled |
| 2 | Remove staging domains from Vercel and Render | Dashboards no longer list staging hostnames |
| 3 | Delete Cloudflare CNAME records for `staging`, `app.staging`, `admin.staging`, and `api.staging` | `dig` no longer resolves the staging hostnames |
| 4 | Pause or delete the staging Supabase project | Supabase dashboard confirms staging project status |
| 5 | Remove staging-only secrets from GitHub, Render, and Vercel | Dashboards show no unused staging secrets |
| 6 | Record teardown evidence in Taskmaster and Airtable | SEC-10 tracker contains teardown note |
